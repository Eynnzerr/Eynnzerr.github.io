WebSocket 为客户端和服务端提供持续的双向消息通道。连接建立后，双方都可以主动发送消息，不必为每次推送重新组织一组 HTTP 请求与响应。

但聊天应用里“这条消息到底发出去了吗”，问的是另一件事：服务端是否收到、是否保存、接收方是否看到。这些状态需要业务协议明确表达。理解 WebSocket 时，我更愿意沿着“建立通道、交换消息、确认结果”这条线往下看。

## 为什么 HTTP 长连接还不够

HTTP/1.1 可以复用连接，HTTP/2 可以在一条连接中多路复用请求。它们减少了传输开销，HTTP 的请求与响应语义仍然存在。

服务端持续向客户端发送数据，也可以使用一个持续开放的 HTTP 响应。例如 SSE 提供面向浏览器的事件流，适合日志、进度和通知等主要从服务端流向客户端的数据。

WebSocket 适合另一种交互：双方都频繁产生事件，发送方向和时机由业务决定。聊天室中的消息、在线协作中的操作、游戏中的输入，都可以作为独立消息进入同一条通道。

| 交互需求 | 较自然的起点 |
| --- | --- |
| 偶尔读取资料、提交一次表单 | HTTP 请求与响应 |
| 服务端持续输出进度或事件 | SSE 等流式响应 |
| 双方持续、低延迟地交换消息 | WebSocket |

通信方向和消息模式决定协议选择的起点，连接数量、代理支持和性能则决定具体部署方案。

## HTTP/1.1 中的升级握手

经典 WebSocket 建连流程使用 HTTP/1.1 Upgrade。若地址是 `wss://`，先建立受 TLS 保护的连接，再发送握手请求。例如：

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: MDEyMzQ1Njc4OWFiY2RlZg==
Sec-WebSocket-Version: 13
```

服务端接受后返回 `101 Switching Protocols`，并提供对应的升级字段和 `Sec-WebSocket-Accept`。客户端验证响应后，双方开始按照 WebSocket 帧格式通信。

`Sec-WebSocket-Key` 是握手随机值。服务端根据规定的算法生成 `Accept`，用于确认对方理解 WebSocket 握手；它没有承担用户登录凭据的职责。账号认证、资源访问权限和浏览器请求的 `Origin` 检查仍应在服务端处理。

这里的 `101` 特指 HTTP/1.1 路径。HTTP/2 使用 RFC 8441 定义的扩展 CONNECT，HTTP/3 则由 RFC 9220 定义相应机制。WebSocket 的建立方式随承载它的 HTTP 版本而变化。

## 消息、帧与 TCP 字节流

经典 WebSocket 位于 TCP 之上。TCP 提供有序字节流，WebSocket 则在字节流上定义消息边界。

一条文本消息可以放在一个帧里，也可以分成多个数据帧传输。分片属于传输组织，业务通常关注的是重组后的完整消息。控制帧可以穿插在分片之间，使 Ping 或 Close 不必总等到一条大消息全部结束。

客户端发送的帧需要掩码处理，服务端发送的帧则不得加掩码。这是 RFC 6455 的协议要求，目的是限制特定的中间设施攻击；掩码密钥本身随帧传输，不提供内容保密性。`wss://` 的机密性和完整性来自 TLS。

这些细节解释了两件事：应用传入一段 JSON 后，在线路上看到的内容并非只有 JSON；网络抓包中的一个 TCP 分段，也不必恰好对应一条业务消息。

## 心跳回答的是哪一层还活着

网络切换、设备休眠或中间代理回收空闲连接，都可能使双方对连接状态的认识暂时不一致。WebSocket 定义了 Ping 和 Pong 控制帧，可用于探测通信端点。

浏览器标准 `WebSocket` API 没有把 Ping/Pong 控制帧直接暴露给 JavaScript。浏览器应用如果需要自己的超时判断，可以约定业务心跳消息，由应用服务器回应。WHATWG 标准明确说明了这个 API 边界。

业务心跳与协议心跳观察的层次不同：

| 收到的响应 | 能据此判断的事情 |
| --- | --- |
| 协议 Pong | 对端协议栈对相应探测作出了回应 |
| 应用 heartbeat 回执 | 对端应用执行了约定的心跳处理逻辑 |
| 某条消息的保存确认 | 服务端完成了该业务协议定义的保存步骤 |

心跳间隔和超时阈值应配合网络环境与网关超时设置。移动端还要考虑后台执行限制：应用没有按时调度心跳，和远端服务器失去响应，是不同的故障原因。

## 最难判断的时刻：保存成功，确认丢了

考虑发送一条聊天消息：

1. 客户端发送消息 `clientMessageId = m42`。
2. 服务端收到消息，并把它保存到数据库。
3. 服务端返回确认。
4. 确认到达客户端之前，网络连接断开。

此时客户端只能确定“没有收到确认”，无法据此判断步骤 2 是否发生。重连后直接生成一个新编号再发送，可能让服务端保存两条相同内容；完全不重试，则可能让真正未送达的消息永远丢失。

一种可行的应用协议是让重试保留相同的 `clientMessageId`，服务端按发送者和消息编号识别重复请求，返回同一次保存结果。确认消息可以约定为“已持久化”，这样客户端收到确认后，就知道服务端已完成哪一步。

对接收方向，可以由服务端为某个消息流分配单调递增的位置。客户端重连时带上最后处理的位置，服务端补发之后的消息；客户端再按稳定标识去重。位置的作用域、历史保留时间和超出保留范围后的全量恢复，都属于这套业务协议的一部分。

TCP 保证的是连接内字节传输的顺序和可靠机制。消息保存、跨连接恢复以及业务副作用去重，需要在它之上继续建立约定。

## 重连和积压也需要有结束条件

网络断开后可以退避重连，并加入随机扰动，减少大量客户端在服务恢复时同时发起连接。用户主动退出、登录状态失效和暂时掉线应区分处理：前两者通常不该无休止地自动重连。

另一种问题发生在连接仍然正常的时候：产生消息的速度高于消费速度。浏览器的 `bufferedAmount` 能反映已排队、尚未发出的数据量；调用 `send()` 也不等于数据已经送到服务端。应用需要决定积压时怎样减速或合并。

例如，光标位置可以保留最新状态，过时的位置更新可以合并；聊天消息则需要逐条保留并确认。为两者使用完全相同的无限队列，会把业务语义差异变成持续增长的内存占用。

实现实时功能时，可以先写清三件事：一条消息的身份是什么，确认表示哪一步完成，断线以后从哪里恢复。通道建立后，这三项约定决定用户看到的功能能否连续工作。
