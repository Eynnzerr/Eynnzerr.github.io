死锁最关键的特征是：参与者等待的条件，只能由同样陷入等待的参与者满足。相互依赖形成闭环后，单纯等待下一次调度已经无法推进执行。

从两把互斥锁开始，就能看清这个闭环怎样形成。

## 两个正确的局部动作，拼成一个无法前进的整体

假设缓存更新需要锁 A，会话更新需要锁 B。线程 T1 先锁 A 再锁 B，线程 T2 则反过来：

| 执行顺序 | T1 | T2 |
| --- | --- | --- |
| 1 | 获得 A | |
| 2 | | 获得 B |
| 3 | 持有 A，等待 B | |
| 4 | | 持有 B，等待 A |

T1 必须等 T2 释放 B，T2 必须等 T1 释放 A。两者都把释放动作放在获得第二把锁、完成工作之后，于是都到不了释放那一步。

这次执行可以画成一条等待链：

```text
T1 → 等待 B → B 由 T2 持有 → T2 等待 A → A 由 T1 持有 → T1
```

加快 CPU、调整线程优先级、延长等待时间，都没有改变这条依赖关系。要恢复进展，必须让其中一个等待条件被解除。

## 四个条件分别落在哪里

在可重复使用资源的经典死锁模型里，上面的情形同时满足四个条件：

| 条件 | 例子中的对应关系 |
| --- | --- |
| 互斥 | A、B 分别只能由一个线程持有 |
| 占有并等待 | T1 持有 A 等 B，T2 持有 B 等 A |
| 不可抢占 | 另一线程不能擅自夺走已被持有的锁 |
| 循环等待 | T1 与 T2 的依赖构成闭环 |

这些条件提供了设计入口。例如，一次性获取所需资源可以改变“占有并等待”，为资源建立统一顺序可以破坏“循环等待”。实际业务往往需要互斥访问，因此统一顺序通常更容易落到代码中。

对于每类资源都只有一个实例的资源分配图，环能够直接揭示死锁；若某类资源有多个可替代实例，判断还取决于可用数量和等待需求。

## 统一顺序为什么有效

规定所有代码都按 `A → B` 的顺序加锁：

```text
T1：获得 A → 获得 B → 完成操作 → 释放 B → 释放 A
T2：获得 A → 获得 B → 完成操作 → 释放 B → 释放 A
```

如果 T1 已经持有 A，T2 会在获得第一把锁之前等待。它尚未持有 B，因而不会阻碍 T1 取得 B、完成工作并释放资源。

推广到更多锁，可以给每把锁规定一个全局一致的等级，只允许按等级递增获取。若循环等待存在，沿着环走一圈，锁等级就必须一直递增，最后又回到原来的等级，这与严格递增矛盾。

这里真正重要的是“全局一致”：两个函数内部各自看起来有序还不够。调用者先持有某把锁，再调用一个内部加锁的函数时，也参与同一条获取链。回调和跨模块调用尤其容易让隐含顺序变长。

例如约定 `sessionLock < cacheLock` 后，持有 `cacheLock` 的代码就不应调用会获取 `sessionLock` 的回调。把回调移出临界区，通常比要求所有回调作者了解内部锁顺序更清晰。Linux 的 [lockdep 文档](https://docs.kernel.org/locking/lockdep-design.html)展示了通过锁依赖关系发现潜在反向获取的问题。

## 超时和重试解决的是哪一步

尝试获取第二把锁失败后，释放已经获得的锁，再稍后重试，可以避免永久占有资源等待。但是所有线程若同时失败、同时释放、同时重试，可能一直忙于互相让路，形成活锁。

退避、加入随机扰动或让竞争者按队列推进，可以减少这类同步重试。无论选择哪种方式，都需要定义失败后的状态：已经完成的修改能否撤销、重试是否会重复执行副作用、释放锁后原先读取的状态是否仍有效。

因此，“给锁加个超时”只提供了退出等待的通道。业务操作如何安全失败、回滚或重试，仍然需要一并设计。

## 安全状态：先问有没有一种完成顺序

锁顺序属于通过结构约束预防死锁。银行家算法则在资源分配前，根据各任务声明的最大需求，判断分配后是否还能找到让所有任务完成的顺序。

考虑只有一种资源、总量为 10 的例子：

| 任务 | 已分配 | 最大需求 | 还可能需要 |
| --- | --- | --- | --- |
| A | 3 | 7 | 4 |
| B | 2 | 4 | 2 |
| C | 2 | 3 | 1 |

已分配总量为 7，因此可用量为 3。可以按 `B → C → A` 推演：

1. B 还需要 2，可用量足够。假设它完成并释放资源，可供后续任务使用的数量从 3 变为 5。
2. C 还需要 1，也能完成。可用量从 5 变为 7。
3. A 还需要 4，最后也能完成。

推演中每完成一个任务，可用量增加的是它**原先已经占有的资源**。临时提供给它、又随着完成归还的那部分，在这次计算里相互抵消了。

现在如果先额外给 A 两个资源，可用量变为 1，而 A、B、C 的剩余需求分别为 2、2、1。仍然可以先完成 C，再完成 B 和 A，所以这次请求能够通过安全性检查。

如果一次额外给 A 三个资源，可用量变为 0，三个任务的剩余需求都大于 0，就无法找出第一个可保证完成的任务。这是一个不安全状态：按照已声明的最大需求，系统失去了完成顺序的保证。若任务实际用不到最大数量，它仍可能提前释放资源。不安全描述的是完成保证已经丢失；死锁描述的是等待已经形成无法自行解除的闭环。

银行家算法适用于能够预先声明最大资源需求的分配场景。普通应用的锁、网络响应和外部回调往往缺少这类完整声明，排查和设计时通常从具体等待关系与锁顺序入手。

## 排查时先还原等待关系

碰到“程序没有反应”，先看线程栈和资源持有者，再决定是否属于死锁。单个线程等待一个很慢的 I/O 是延迟问题；长期得不到调度或竞争不到资源可能是饥饿；线程不断改变状态却无法完成任务可能是活锁。

死锁排查的核心证据是一条闭合的等待链。找到它以后，再选定要改变的获取顺序、临界区范围或失败退出路径，修复才会对应到具体原因。
