YuukaTalk 的长图导出遇到过两类问题：图片素材偶尔变成空白，以及对话过长时内存压力过大。它们最后汇合成同一个设计问题：**渲染当前内容之前，要把需要的图片准备好；渲染结束之后，要尽快释放不再需要的图片。**

如果只追求“全部提前加载”，空图问题可能减轻，但内存峰值会随着对话长度增长。如果只追求“尽量不缓存”，测量和绘制又可能拿不到图片。我的处理方式是把导出拆成窗口，用明确的资源就绪顺序配合两类内存预算。

## 空图为什么会出现在导出里

聊天界面使用异步图片组件是自然的选择。页面可以先显示占位内容，图片完成加载后再刷新。

离屏导出没有这样的等待过程。导出代码创建 item，调用测量、布局和绘制，然后就继续处理下一个 item。如果执行到 `draw()` 时图片仍在加载，当前这一帧就只能画出占位内容。图片尺寸还可能参与高度计算，于是错误既可能出现在像素上，也可能出现在布局上。

问题的时间顺序大致是：

```text
创建图片 item
    → 发起异步图片请求
    → measure / layout
    → draw 到导出画布
    → 图片请求完成，触发稍后的界面更新
```

最后一步来得太晚，已经导出的像素不会因此自动更新。

导出需要的是另一种顺序：

```text
收集当前窗口的图片
    → 等待这些图片加载完成
    → 使用已准备好的 Bitmap 创建 item
    → measure / layout / draw
    → 释放当前窗口的图片
```

这里“等待加载完成”是导出协程与加载工作的先后关系。图片解码仍放在 IO 上下文里，View 的测量、布局和绘制留在主线程。

## 把图片来源从组件中抽出来

我在导出路径中加入了 `ExportImageResolver`。它提供按来源查找照片和头像的接口，由窗口管理器准备缓存，再通过 `CompositionLocal` 传给下层的图片组件。

于是同一个组件具有两种读取方式：

| 使用场景 | 图片来源 |
| --- | --- |
| 正常浏览聊天 | 使用 Coil 异步加载 |
| 离屏导出 | 从 resolver 中读取当前已经准备好的 Bitmap |

这种做法让导出组件在测量时就能看到确定的图片内容，也把缓存管理集中在导出过程里。图片加载失败仍要决定是展示失败占位还是终止导出；资源就绪顺序解决的是加载尚未完成的竞争问题。

导出请求还会指定显示所需尺寸，关闭 crossfade 和硬件 Bitmap。前者避免导出一个过渡帧，后者适配绘制到软件 Bitmap 的路径。导出缓存由 resolver 管理，因此这条请求路径也关闭了 Coil 的内存缓存，避免把导出资源额外留在共享缓存中。

## 两遍遍历：先知道长图有多高，再真正画出来

最终长图需要一次确定宽高，而消息 item 的高度要测量后才能知道。因此实现采用了两遍遍历。

第一遍按窗口准备资源，创建并测量每一个 item，只保留高度数组与总高度；一个窗口结束后释放照片缓存。第二遍创建最终输出 Bitmap，再按同样的窗口重新准备图片，把 item 依次画到对应的纵向位置。

```text
第一遍
窗口 A：准备图片 → 测量高度 → 释放照片
窗口 B：准备图片 → 测量高度 → 释放照片
……
汇总输出宽高 → 检查输出预算 → 创建最终 Bitmap

第二遍
窗口 A：准备图片 → 按偏移绘制 → 释放照片
窗口 B：准备图片 → 按偏移绘制 → 释放照片
……
返回最终 Bitmap
```

这会让某些图片在两遍中各解码一次，代价是额外的加载和解码工作，换来的收益是不用同时持有整段对话的图片资源。测量和绘制之间，对话内容及尺寸配置也应保持一致，否则第一遍得到的高度就不再可靠。

这个过程分窗口的是**输入图片的准备和缓存**。第二遍仍然需要一张完整的输出 Bitmap，所以还必须单独限制最终产物的大小。

## 第一类预算：解码缓存

实现使用 `Runtime.getRuntime().maxMemory()` 作为预算参考，先计算总解码预算，再分给头像和聊天照片：

$$
B_{\text{decode}}=\operatorname{clamp}\left(\frac{M}{10},12\text{ MiB},48\text{ MiB}\right).
$$

头像复用频繁且尺寸较小，使用独立 LRU 缓存；照片占用较大，按窗口保存。当前规则是：

$$
B_{\text{avatar}}=\max\left(2\text{ MiB},\min\left(8\text{ MiB},\frac{B_{\text{decode}}}{4}\right)\right),
$$

$$
B_{\text{photo}}=\max\left(8\text{ MiB},B_{\text{decode}}-B_{\text{avatar}}\right).
$$

这几个比例是项目采用的经验预算。Android 3.0 到 7.1 的 Bitmap 像素存储在托管堆中，Android 8.0 起转到 native heap。因此在新系统上，`maxMemory()` 适合作为保守参考，不能直接表示剩余可用的 Bitmap 内存。[Android 的内存说明](https://developer.android.com/topic/performance/graphics/manage-memory)列出了这段平台变化。

分窗口时，先用显示宽度估计单张照片的解码开销。若宽度是 $w$，把高度上限估为 $3w$，按 ARGB_8888 计算：

$$
B_{\text{one}}=w\times3w\times4.
$$

再以照片预算除以单张估算值，得到窗口中允许的照片数量；实现还给每个窗口加上了 80 条消息的数量上限。

例如，假设 $M=256\text{ MiB}$、照片显示宽度为 720 像素：

| 项目 | 估算结果 |
| --- | --- |
| 解码总预算 | 约 25.6 MiB |
| 头像预算 | 约 6.4 MiB |
| 照片预算 | 约 19.2 MiB |
| 单张照片，按 $720\times2160\times4$ | 约 5.93 MiB |
| 每个窗口的照片数量 | 3 张 |

这是按预算公式推导的例子。实际缓存还会根据解码后的像素分配量 `allocationByteCount` 调整；预估尺寸、解码器临时分配和实际图片尺寸会影响运行时峰值。

## 第二类预算：最终输出长图

输入图片分窗口处理之后，最终输出仍可能非常大。

一张 $1080\times30000$ 的 ARGB_8888 长图，仅像素数据就约为

$$
1080\times30000\times4\approx123.6\text{ MiB}.
$$

因此创建输出 Bitmap 之前，需要先计算 `width × height × 4`。实现给最终像素数据设置的参考上限是 $0.55M$，超出后抛出明确的导出尺寸异常，引导用户选择分段导出。

计算字节数时先将宽高转为 `Long`，再相乘，避免中间的 `Int` 溢出让过大的图通过检查。

通过输出预算后，创建 Bitmap 仍然可能因当时的内存状态失败。预算判断的作用是提前筛掉明显过大的任务，并把“长图过大”变成用户能理解、能处理的反馈。

第二遍绘制时，输出 Bitmap、当前窗口照片、头像缓存和临时渲染对象会同时存在。评估峰值时要把它们加在一起，不能只看最终长图。

## 像素格式降级放在哪一层

照片缓存接近预算时，可以尝试 RGB_565。它通常使用每像素 2 字节，没有 alpha 通道，颜色精度也低于 ARGB_8888，适合在能够接受画质变化的照片上作为降级选项。

这里应分清两个对象：

- **输入照片**可以根据剩余缓存预算选择像素格式。
- **最终输出 Bitmap**在当前导出路径中仍按 ARGB_8888 估算和创建。

降低输入照片的格式，会减轻输入缓存占用，却不会自动让最终长图减半。输出尺寸超过预算时，当前路径采用分段导出的反馈。

回收同样依赖资源的所有权。导出缓存里独占的 Bitmap，只有在 item 已经完成使用、相关视图被释放后才能回收；共享图片缓存中的对象不应该由临时使用者随意 `recycle()`。

## 这次改动真正整理的是资源生命周期

空图与 OOM 很容易被当成两个独立问题。沿着导出过程往下看，它们都取决于图片在什么时刻存在、由谁持有、何时释放。

最终的顺序是：窗口内准备资源，让测量和绘制拿到确定的图片；窗口结束就释放照片，把高复用的头像限制在独立缓存里；在创建最终长图之前，再检查产物本身的预算。

以后如果要进一步支持更长的内容，重点会落到输出端：直接生成多张图片，或者使用支持增量写出的输出方案。把输入分窗口解决之后，最终那张完整 Bitmap 就成为下一处需要改变的数据结构。
