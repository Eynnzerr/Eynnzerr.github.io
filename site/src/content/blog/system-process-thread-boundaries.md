进程描述程序拥有怎样的资源和地址空间，操作系统线程描述一条可以被内核调度的执行流，Java 线程则是运行时提供给开发者的并发抽象。资源归属、执行调度和运行时抽象，分别决定了程序的隔离方式、等待关系和任务承载成本。

设想一个客户端正在下载文件，同时响应界面输入。下载任务等待网络数据时，界面仍然应该能够处理事件。要解释这件事，需要依次回答：资源是否共享、谁在等待、谁能够继续获得 CPU。

## 进程提供资源环境，线程推进执行

一个进程可以拥有多个线程。以常见的 Linux/POSIX 线程模型为例，同进程线程共享虚拟地址空间、打开的文件描述符等进程资源，各自保留寄存器上下文、线程栈和线程标识等执行状态。

| 内容 | 同一进程内的线程之间 |
| --- | --- |
| 堆、全局数据、地址映射 | 共享 |
| 打开的文件描述符 | 共享 |
| 当前执行位置、寄存器上下文 | 分别维护 |
| 线程栈 | 分别使用 |
| 线程局部数据 | 按线程组织 |

“每个线程有自己的栈”说的是分配和使用方式。栈仍然位于进程共同的地址空间中，线程之间并没有因为使用不同的栈就获得进程级的内存隔离。若通过有效指针访问到另一线程的栈内存，仍然需要处理对象生命周期和同步。

共享让线程交换数据很方便，也让错误更容易扩散。同一进程中的线程可能访问同一个对象，因而需要互斥、原子操作或明确的消息传递规则。独立进程则以独立地址空间为基础，通常通过 IPC 显式交换数据。[pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html)列出了共享资源和线程独有属性。

## 等网络和等 CPU，是两种等待

下载线程调用阻塞式读取后，如果当前没有数据，它需要等待网络事件。此时即使给它更多 CPU 时间，也不能凭空产生待接收的数据。界面线程若已经有事件可处理，就可以被调度执行。

用经典状态模型表示，过程如下：

| 时刻 | 下载线程 | 界面线程 | 发生的事情 |
| --- | --- | --- | --- |
| 1 | 运行 | 就绪 | 下载线程准备读取数据 |
| 2 | 阻塞 | 运行 | 网络暂时无数据，界面开始处理输入 |
| 3 | 就绪 | 运行 | 数据到达，下载线程具备继续运行的条件 |
| 4 | 运行 | 就绪或等待 | 调度器安排下载线程继续执行 |

事件到达使线程重新变得可运行；是否马上运行，还要经过调度。就绪表示在等待 CPU，阻塞表示还缺少其他继续执行的条件。

并发描述多个任务的执行过程可以交错推进；并行描述某个时刻确实有多个任务同时执行。并发程序可以在单个逻辑 CPU 上轮流运行，也可以在多个逻辑 CPU 上并行运行。

## 权限切换不等于任务切换

用户态和内核态区分的是当前代码的执行权限。程序通过系统调用请求内核完成文件访问、网络通信等工作时，可能先进入内核，随后继续返回同一个线程。

任务切换则要保存一个执行流的上下文，并恢复另一个执行流。系统调用是否触发任务切换，取决于调用过程是否需要阻塞，以及当时的调度决定：

```text
数据已经可读：用户线程 → 内核处理 read → 返回原线程
需要等待数据：用户线程 → 内核处理 read → 线程睡眠 → 调度其他线程
```

同一进程的两个线程切换时，可以继续使用相同的地址空间；跨进程切换通常还要切换内存上下文。具体成本还受到缓存状态、硬件地址空间标识、调度路径等因素影响。

这也解释了为什么增加线程数量并不必然提高速度：如果瓶颈是 CPU 计算或同一把锁，更多可运行线程可能只是增加竞争和调度工作。若大量任务主要在等待独立的 I/O，则并发执行更有机会提高资源利用率。

## Java 的 Thread 还要再分两类

传统 HotSpot 平台线程通常与操作系统线程一一对应。Java 中的 `Thread` 对象管理线程名称、Java 层状态、中断等语义，底层执行仍由对应的 OS 线程承载。

JDK 21 将虚拟线程正式纳入 Java 平台。虚拟线程同样是 `java.lang.Thread`，但不在整个生命周期中独占一条 OS 线程。JDK 调度器把它挂载到作为 carrier 的平台线程上执行；在受支持的阻塞操作中，可以卸载它，让 carrier 承载其他虚拟线程。

```text
Java 任务
  ├─ 平台线程 → 对应的 OS 线程 → 操作系统调度
  └─ 虚拟线程 → JDK 调度器 → carrier 平台线程 → 操作系统调度
```

虚拟线程优化的是大量并发任务等待时的承载成本。计算任务的并行程度仍取决于任务拆分方式和可用 CPU；阻塞时能否卸载，则取决于具体 JDK 版本和调用方式。[JEP 444](https://openjdk.org/jeps/444)说明了平台线程、虚拟线程和 carrier 的关系。

`new Thread(...)` 仍创建平台线程。要使用虚拟线程，需要选择相应的 API，例如 `Thread.ofVirtual()` 或虚拟线程执行器。Java 线程与 OS 线程的对应关系，因而取决于所用的线程类型。

## 线程转储里的状态该怎样读

Java 的 `Thread.State` 从 JVM 的角度分类线程状态。官方 API 对 `RUNNABLE` 的定义包含了可能在等待操作系统资源的情形，操作系统的调度状态需要另行观察。

| Java 状态 | 应关注的含义 |
| --- | --- |
| `RUNNABLE` | JVM 认为线程可运行，不等于此刻一定占有 CPU |
| `BLOCKED` | 等待进入一个 `synchronized` 监视器 |
| `WAITING` | 无超时地等待某个动作，例如特定的 `wait`、`join` 或 `park` |
| `TIMED_WAITING` | 带时间限制的等待 |

看到很多 `RUNNABLE` 时，结合 CPU 使用率与调用栈判断它在执行什么；看到 `BLOCKED` 时，检查监视器的持有者；看到 `WAITING` 时，追踪它在等待什么事件。状态和调用关系结合起来，才能定位进展停在了哪里。

进程边界帮助确定资源归属，线程状态帮助确定执行在哪里停下，运行时模型帮助确定这些任务由谁承载。把这三个问题分开，分析并发程序时才能沿着实际等待关系往下查。
